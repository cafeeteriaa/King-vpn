# KING VPN — VPN Engine Integration Discovery

**Branch:** `integration/vpn-engine-discovery`  
**Base:** `main` at `eabddd63368f43ebdec8a634b04ced94b6d72da0`  
**Status:** Discovery/architecture baseline only. Nothing in this document is claimed to be integrated or operational.

## Non-negotiable architecture

1. Preserve the existing Xray/V2Ray path and all current app features, data, settings, package identity, signing compatibility, routing, DNS, IPv4/IPv6, Smart Pilot, failover, diagnostics and rollback behavior.
2. Use one Android `VpnService` / TUN owner for the app. Android permits only one active VPN service per user/profile; starting another service stops the active one. Engines must therefore be mutually exclusive at the TUN ownership layer, while local proxy engines may be composed behind the shared TUN only where their data paths support it.
3. Define an engine adapter contract: capability discovery, config validation, permission preparation, start, state/events, traffic counters, stop, health/data-plane proof, diagnostics, resource usage and cleanup. Never mark an engine operational based on a parser, UI tile, process launch or a core CONNECTED event alone.
4. Keep engines independent: protocol-specific configuration, lifecycle, logs and failure states must not silently fall through to a different engine. Smart Pilot may select another engine only when the user has selected automatic mode and the target engine has passed compatibility and real data-plane checks.
5. Each integration must have an upstream/version pin, source provenance, license and notice review, ABI coverage, supply-chain/hash verification, unit tests, Android lifecycle tests, IPv4/IPv6/DNS/route tests, traffic leak checks, resource measurements and rollback.
6. This discovery branch does not remove any existing feature and does not introduce placeholder engines. A feature is listed as integrated only after executable code and tests exist.

## Evidence and important compatibility notes

- Android's VPN API requires a service derived from `VpnService`, a protected manifest declaration, `VpnService.prepare()`, `protect()` for tunnel sockets and a TUN established through `VpnService.Builder`. Android documents that only one VPN service is active per user/profile.
- Psiphon upstream documents an Android AAR/Maven artifact and source-build route, but the indexed upstream project declares GPL-3.0. This is a distribution/license gate, not merely a Gradle dependency.
- VPN Gate's Android instructions list OpenVPN and L2TP/IPsec; its server ecosystem also exposes SoftEther and other protocols. A community Android connector demonstrates SoftEther/OpenVPN/SSTP adapters, but its GPL-3.0 license must be assessed independently.
- nthLink's Android repository describes an app framework using Leaf and nthlink-outline SDKs, with backend and VPN-client integration points.
- Shroudly's repository describes a portable C engine and Android NDK build path. The exact TUN/proxy integration and redistribution terms still require source-level review.
- Ceno's Android build consumes Ouinet and GeckoView-related libraries; this is browser-scoped and must not be presented as a full-device VPN.
- ByeDPI has an Android VpnService implementation. Its integration must not create a competing VPN service.
- PowerTunnel Android is based on NetGuard's VPN server and a local proxy. Its own README states that Play Store publication requires permission; license and permission review are a hard precondition.
- I2P's embedding documentation shows Java router embedding but says an Android router service library is on its roadmap; a direct embedding would require careful state/lifecycle management.\n- Tor Project's Arti Android guide says the Rust API is not yet stable and proper JNI bindings are not provided; a production Android adapter therefore needs maintained bindings and device validation.\n- Lantern's current upstream describes compiling its Go Core into an Android AAR via gomobile; the repository is GPL-3.0 and its Android app owns a VpnService, so TUN teardown/handoff and license compatibility are mandatory.

## Execution order

1. Finish source-level audit of the current shared TUN owner and define the adapter interface without changing existing Xray behavior.
2. Integrate the most directly embeddable, independently licensed cores first: Psiphon and sing-box/Leaf-family engines after dependency/license verification.
3. Add protocol/service adapters for VPN Gate (SoftEther/OpenVPN/SSTP), then Tor and I2P with explicit bootstrap and shutdown state machines.
4. Add proxy/TUN composition for Shroudly, ByeDPI and PowerTunnel only after proving they can coexist behind the shared TUN without nested VPN ownership or traffic loops.
5. Add Ceno as a separately labeled browser feature, not a full-device VPN.
6. Pursue Cloudflare WARP, Lantern and Avira only through supported SDKs, documented integration interfaces or authorized partner agreements.
7. Add CalyxVPN after verifying its maintained upstream source, core and licensing.
8. Run three independent reviews for each substantial change: architecture/lifecycle; security/license/network correctness; regression/build/test coverage.

## Acceptance state vocabulary

- `DISCOVERED`: upstream and product type identified.
- `EVALUATED`: source, interface, license, Android compatibility and resource cost reviewed.
- `APPROVED`: permitted and technically suitable for this app.
- `INTEGRATED`: executable adapter/core included in the build.
- `TESTED`: automated tests and Android lifecycle/data-plane tests passed.
- `OPERATIONAL`: real device traffic, leak, stability and resource validation passed.
- `INCOMPATIBLE` / `UNAVAILABLE`: reason and evidence recorded; do not fake support.

No engine is currently promoted beyond discovery by this document.
