# King AI — مهندس نرم‌افزار محلی

## اصل معماری

نویسنده کد باید مدل زبانی محلی داخل King VPN باشد. Google فقط برای کشف منابع فنی و مستندات رسمی استفاده می‌شود؛ جست‌وجوگر یا وب‌سایت منبع کد نیست. هیچ API پولی یا کلید سرویس هوش مصنوعی برای استنتاج مدل لازم نیست.

## آنچه اکنون در شاخه توسعه پیاده‌سازی شده است

1. **استنتاج محلی:** `lib/king_local_ai.dart` از `local_inference_flutter` و `llama.cpp` برای اجرای GGUF روی دستگاه استفاده می‌کند. مدل اولیه Qwen2.5-Coder-1.5B-Instruct Q4_K_M است؛ فایل حدود 1.12 GB بوده و با URL نسخه‌بندی‌شده، اندازه و SHA-256 دقیق دریافت می‌شود. وزن مدل داخل APK قرار نمی‌گیرد.
2. **کنترل سازگاری دستگاه:** پیش از دانلود، API اندروید، ABI و 64-bit بودن از طریق `LocalInferenceFlutter.checkDeviceSupport()` بررسی می‌شود. حداقل‌های مدل 5 GB RAM فیزیکی، 1.8 GB حافظه آزاد و 1.8 GB فضای آزاد ذخیره‌سازی هستند. دانلود از ModelManager با قابلیت ادامه و اعتبارسنجی انجام می‌شود.
3. **تحقیق Google:** جست‌وجوی HTML گوگل فقط برای کشف URL استفاده می‌شود. صفحات HTTPS از فهرست دامنه‌های رسمی مجاز دریافت می‌شوند؛ متن صفحه به‌عنوان داده غیرقابل‌اعتماد به مدل داده می‌شود، نه دستور. این روش API رسمی Google نیست و ممکن است با CAPTCHA، محدودیت منطقه یا تغییر HTML از کار بیفتد.
4. **حافظه تحقیق:** URL، عنوان، زمان دریافت و گزیده منابع رسمی در فایل محلی `king_ai_research_memory.jsonl` ذخیره می‌شود؛ حداکثر 200 رکورد نگه داشته و حداکثر سه منبع مرتبط به درخواست بعدی افزوده می‌شود. این حافظه بازیابی دانش است، نه آموزش مجدد وزن‌های مدل.
5. **اتصال GitHub:** توکن کاربر در `FlutterSecureStorage` نگهداری می‌شود و وارد prompt یا log نمی‌شود. مدل می‌تواند فایل‌های محدود مخزن را بخواند، پیشنهاد تغییر بسازد و از GitHub Git Data API شاخه جدا و Pull Request ایجاد کند.
6. **دروازه ایمنی تغییر:** مسیرها به `lib/`، `test/` و `tools/` محدودند؛ فایل‌های خارج از context رد می‌شوند؛ حداکثر شش فایل context، 7.5 KB متن ورودی، سه فایل تغییر و بررسی الگوهای secret اعمال می‌شود. تغییر مستقیم شاخه اصلی و merge خودکار وجود ندارد.
7. **اعتبارسنجی تغییر:** ایجاد PR باعث اجرای workflow تست، analyzer و APK build می‌شود. ادغام فقط پس از بررسی انسانی diff و نتیجه CI مجاز است.
8. **مشاور واقعی خلبان:** وقتی مدل روی دستگاه بارگذاری شده و خلبان وارد فاز ضعف/بازیابی یا تصمیم کم‌اطمینان می‌شود، مدل محلی هر ۶ دقیقه حداکثر یک بار شواهد شبکه را مرور می‌کند. خروجی فقط یک اقدام محدود JSON است؛ گیت‌های قطعی اتصال، زمان نگه‌داری، وجود سرور سالم و وضعیت نت ملی قبل از هر اثرگذاری بررسی می‌شوند. در صورت خطا/timeout، خلبان قطعی قبلی بدون توقف ادامه می‌دهد.
9. **بازخورد CI و اصلاح مرحله‌ای:** عامل می‌تواند وضعیت checkهای Pull Request را برای commit دقیق بخواند، annotationهای خطا و مراحل شکست‌خوردهٔ GitHub Actions را جمع‌آوری کند، log job ناموفق را با سقف حجم دریافت و پیش از ورود به prompt توکن‌ها/کلیدهای رایج را حذف کند. مدل محلی با context محدود مخزن یک اصلاح پیشنهاد می‌دهد و فقط یک PR پیگیری روی شاخهٔ PR قبلی می‌سازد. سقف زنجیره دو تلاش برای PR ریشه است؛ تلاش‌ها بین PRهای پیگیری نیز حفظ می‌شوند. هیچ merge، retry نامحدود یا انتشار خودکار انجام نمی‌شود. این چرخه فعلاً با فراخوانی صریح API از طرف برنامه/اپراتور اجرا می‌شود، نه به‌صورت daemon یا واکنش خودکار به هر رویداد GitHub.

## چرخه فعلی

`User task → Google discovery → official-source retrieval → local model reasoning → structured file changes → path/secret gate → GitHub branch → Pull Request → GitHub Actions CI → human review`

## محدودیت‌های صریح نسخه فعلی

- مدل 1.5B یک مدل کوچک موبایلی است و توانایی آن هم‌سطح مدل‌های بزرگ ابری یا ChatGPT نیست؛ برای اصلاحات دشوار ممکن است context بیشتری لازم باشد یا پیشنهاد نادرست بدهد.
- context مخزن محدود است و همه فایل‌های بزرگ یا وابستگی‌های چندلایه را در یک نوبت نمی‌خواند.
- چرخه CI در این شاخه پیاده شده، اما هنوز دکمه/صفحهٔ کاربری آن به رابط تنظیمات اپ متصل نشده است؛ اجرای آن فعلاً از طریق API برنامه‌نویسی و با فراخوانی صریح انجام می‌شود.
- دسترسی به checkها، annotationها و logها به مجوزهای GitHub token وابسته است؛ اگر مجوز یا log در دسترس نباشد، عامل باید از شواهد ناقص نتیجه‌گیری نکند و ممکن است اصلاح را متوقف کند.
- این چرخه حداکثر دو PR پیگیری برای هر PR ریشه می‌سازد؛ merge و انتشار همچنان انسانی است.
- مدل هنوز وزن‌های خودش را بازآموزی یا جایگزین نمی‌کند. ارتقای فعلی از طریق حافظه تحقیق و PRهای کد انجام می‌شود. ارتقای نسخه مدل باید جداگانه، با manifest امضاشده/هش، آزمون کیفیت و rollback اضافه شود.
- Google HTML scraping یک روش best-effort است، نه تضمین دسترسی همیشگی.
- ساخت APK در CI و اجرای واقعی مدل روی دستگاه فیزیکی دو آزمون جدا هستند. تا وقتی CI سبز و اجرای مدل روی گوشی تأیید نشده، قابلیت را production-ready نمی‌نامیم.

## گام‌های بعدی ضروری

1. سبز کردن CI برای وابستگی native llama.cpp و APK اندروید.
2. اجرای مدل روی دستگاه arm64 API 28+ و سنجش RAM، گرما، سرعت و مصرف باتری.
3. افزودن بازیابی دقیق‌تر فایل/نماد و context چندفایلی مبتنی بر خطا.
4. اتصال API چرخه CI به رابط کاربری با نمایش شواهد، diff، تعداد تلاش باقی‌مانده و وضعیت PR پیگیری؛ حفظ تأیید انسانی پیش از هر merge.
5. ارتقای نسخه مدل فقط با checksum، منبع و مجوز معتبر، benchmark ثابت، آزمون امنیتی و حفظ نسخه قبلی.
6. گسترش مجوز تغییر فایل‌ها فقط بعد از افزودن تست اختصاصی برای هر دسته؛ فایل‌های امضا، مجوز، VPN native، Gradle و CI همچنان محافظت‌شده می‌مانند.

مدل و وزن‌ها جدا از APK توزیع می‌شوند. مدل اولیه Qwen2.5-Coder تحت Apache-2.0 است؛ مجوز مدل و noticeهای native runtime باید همراه برنامه در صفحه مجوزها قابل مشاهده باشند.


## مقیاس‌پذیری هدف یک میلیون کاربر

نسخه فعلی یک عامل توسعه محلی/کلاینتی و اتصال GitHub است، نه زیرساخت آماده برای یک میلیون کاربر هم‌زمان. پیش از انتشار عمومی در این مقیاس، این اجزا لازم‌اند:

- **Control plane stateless:** احراز هویت، ثبت نسخه کلاینت، پیکربندی منطقه‌ای و feature flags؛ بدون نگهداری وضعیت حساس در حافظه فرایند.
- **Job queue:** صف پایدار برای تحلیل crash/CI و انتشار دانش، با idempotency key، retry محدود، dead-letter queue و اولویت‌بندی.
- **Artifact registry:** نگهداری مدل‌ها، manifest امضاشده، hash، حداقل نسخه اپ، ABI، اندازه، مجوز و امکان rollback.
- **مدل چندسطحی:** مدل کوچک محلی برای همه دستگاه‌های سازگار؛ مدل بزرگ‌تر فقط در workerهای مقیاس‌پذیر و در صورت وجود زیرساخت و سیاست حریم خصوصی. هیچ درخواست یا داده خصوصی بدون رضایت به سرویس بیرونی ارسال نمی‌شود.
- **حریم خصوصی چندمستاجری:** جداسازی داده و حافظه هر کاربر/نصب؛ دانش مشترک فقط از داده‌های ناشناس و opt-in که از نظر امنیتی و کیفیت تأیید شده‌اند.
- **قابلیت اطمینان:** rate limit، backpressure، circuit breaker، timeout، cache، telemetry حداقلی و SLO برای API/دانلود/انتشار.
- **زنجیره عرضه امن:** امضای artifact، provenance، SBOM، اسکن وابستگی، canary rollout، kill switch و بازگشت خودکار به نسخه قبلی.
- **مهندسی کد در GitHub:** محیط ایزوله برای هر job، توکن کوتاه‌عمر با حداقل دسترسی، شاخه مجزا، تست/analyzer/build، بررسی diff و تأیید انسانی قبل از merge.

## سیاست خودتوسعه‌ی مرحله‌ای تا یک میلیون کاربر

به دستور معماری به King AI اضافه شده است که یک میلیون کاربر را هدف بلندمدت بداند، اما فقط مرحله بعدیِ اثبات‌شده را پیاده کند؛ نه اینکه همه زیرساخت را از روز اول بسازد. این سیاست فعلاً یک دستور و نقشه مهندسی برای عامل کدنویس است؛ چون هنوز control plane و آمار فعال کاربران مستقر نشده، عامل در نسخه فعلی نمی‌تواند تعداد کاربران واقعی را از راه دور مشاهده یا به‌صورت خودکار بر اساس آن trigger شود.

- **مرحله پایه / تا حدود ۱k نصب فعال:** بهینه‌سازی مصرف RAM/CPU/باتری، دانلود مدل و artifact با hash، گزارش خطای opt-in و حفظ عملکرد آفلاین.
- **مرحله رشد / حدود ۱k تا ۱۰k کاربر فعال:** فقط در صورت نیاز واقعی، افزودن control plane سبک، آمار ناشناس و opt-in، feature flags، محدودسازی نرخ و داشبورد سلامت.
- **مرحله توزیع / حدود ۱۰k تا ۱۰۰k:** صف job پایدار، CDN منطقه‌ای مدل و به‌روزرسانی، cache، backpressure و کنترل هزینه هر job.
- **مرحله چندمنطقه‌ای / حدود ۱۰۰k تا ۱M:** چند منطقه مستقل، تقسیم بار، registry مقاوم artifact، disaster recovery و آزمون بار/خرابی در مقیاس.
- **در هر مرحله:** عامل باید شواهد مصرف و latency را بخواند، bottleneck را مشخص کند، یک تغییر کوچک و برگشت‌پذیر در PR بسازد، تست و load test همان مرحله را اجرا کند و فقط پس از بررسی انسانی merge شود. اگر معیارها بهبود نداشتند، تغییر باید rollback شود.

آستانه‌های بالا نقطه شروع برنامه‌ریزی‌اند، نه سقف یا تضمین ظرفیت. trigger واقعی باید بر اساس کاربران فعال روزانه، نرخ خطا، p95 latency، queue depth، مصرف پهنای باند و هزینه زیرساخت تنظیم شود.

تا پیش از استقرار و آزمون بار واقعی، ظرفیت یک میلیون کاربر ادعا نمی‌شود. این هدف باید با آزمون بار تدریجی (۱k، ۱۰k، ۱۰۰k و سپس ۱M)، سنجش latency/error rate و هزینه هر کاربر اثبات شود.


## Revision 68 — مهندسی چندمرحله‌ای و یک PR یکپارچه

در مسیر درخواست‌های تعاملی مالک، تولید تغییر از یک پاسخ تک‌مرحله‌ای به خط لولهٔ چندمرحله‌ای تبدیل شده است:

1. مدل ابتدا یک برنامهٔ وابستگی‌محور با ۱ تا ۶ مرحله تولید می‌کند؛ این مرحله فقط برنامه‌ریزی است و کد نمی‌نویسد.
2. هر مرحله context مستقل و محدود خودش را از فایل‌های موجود lib/، test/ و tools/ می‌گیرد؛ حداکثر ۶ فایل و ۷۵۰۰ نویسه در هر نوبت.
3. هر نوبت تولید حداکثر ۳ فایل تغییر می‌دهد. خروجی مراحل قبلی، اگر در مرحلهٔ بعد دوباره لازم باشد، به‌عنوان ورودی جدید داده می‌شود؛ استفاده از نسخهٔ قدیمی فایل باعث رد تعارض می‌شود.
4. حداکثر ۱۸ فایل و ۱۸۰٬۰۰۰ نویسهٔ محتوای نهایی در یک بسته جمع می‌شود. همهٔ مراحل باید کامل و اعتبارسنجی شوند؛ سپس یک commit در Git Data API و فقط یک Draft Pull Request ساخته می‌شود. پیش از مرحله‌ها SHA شاخهٔ main ثبت می‌شود؛ تمام contextها از همان commit خوانده می‌شوند و اگر main قبل از ثبت PR جلو برود، ساخت PR متوقف می‌شود تا خروجی قدیمی روی نسخهٔ جدید نوشته نشود.
5. اگر context یک مرحله موجود نباشد، خروجی مدل نامعتبر باشد، تعارض نسخه رخ دهد یا بودجهٔ بسته رد شود، PR ناقص ساخته نمی‌شود.
6. مالک باید diff کامل و نتیجهٔ CI دقیق همان commit را بررسی کند. هیچ merge، انتشار APK یا release خودکاری انجام نمی‌شود.

### مرزهای ایمنی و محدودیت‌های باقی‌مانده

- این خط لوله فقط برای درخواست تعاملی و احراز هویت‌شدهٔ مالک است. ممیزی خودکار پس‌زمینه همچنان حداکثر دو فایل تغییر می‌دهد و یک پیشنهاد محدود و قابل بازبینی می‌سازد.
- مسیرهای قابل تغییر مدل محلی همچنان به فایل‌های موجود در lib/، test/ و tools/ محدودند. ایجاد فایل جدید و تغییر Native Android، Gradle، dependency، CI، signing و سیاست امنیتی در مسیر خودکار مدل مجاز نشده است.
- محدودیت ۳ فایل برای هر inference pass حذف نشده؛ به‌جای آن، چند pass محدود و وابسته به هم در یک PR واحد جمع می‌شوند. این کار با مدل موبایلی 1.5B سازگارتر از فرستادن کل پروژه در یک prompt بزرگ است.
- افزایش سقف PR به ۱۸ فایل، ظرفیت اثبات‌شدهٔ مدل یا تضمین کیفیت نیست؛ صحت فقط با بازبینی diff، تست و CI دقیق HEAD مشخص می‌شود.
- تست‌های جدید test/king_ai_change_pipeline_test.dart برنامهٔ مرحله‌ای، ترتیب مراحل، ادغام خروجی، تعارض نسخه، مسیرهای نامعتبر و بودجهٔ فایل را پوشش می‌دهند. تا پیش از اجرای workflow دقیق HEAD، این تست‌ها اجراشده محسوب نمی‌شوند.
