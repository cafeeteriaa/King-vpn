# King AI — مهندس نرم‌افزار خودمختار

## هدف محصول

نویسنده و اصلاح‌کننده کد باید خودِ مدل هوش مصنوعی داخل King VPN باشد. Google، وب و مخازن عمومی فقط منابع تحقیق و مستندات هستند؛ هیچ‌کدام نویسنده کد محسوب نمی‌شوند. موتور باید بتواند کد Dart، Kotlin، Gradle و Python را بخواند، وابستگی فایل‌ها را دنبال کند، تغییر چندفایلی پیشنهاد دهد، تست بنویسد و نتیجه را از روی شواهد ارزیابی کند.

## تفکیک اجزای ضروری

1. **مدل کدنویس محلی (ضروری و هنوز پیاده‌سازی‌نشده):** یک مدل زبانی آموزش‌دیده برای کدنویسی با inference محلی روی دستگاه یا runtime محلی مورد اعتماد. مدل باید context چندفایلی، تولید diff ساختاریافته، ادامه کار و محدودیت مصرف RAM/CPU داشته باشد. جست‌وجوی وب، rule engine یا template جایگزین این مدل نیست.
2. **موتور ابزار (قابل ساخت مستقل از مدل):** خواندن فایل‌های مجاز، جست‌وجوی نمادها، تحلیل خطا، اجرای تست و build، خواندن خروجی ابزارها و بازگرداندن شواهد به مدل.
3. **حافظه مهندسی:** نگهداری خلاصه پروژه، خطاهای تکراری، patchهای پذیرفته/ردشده، نتایج تست و نسخه مدل؛ بدون ذخیره UUID، لینک کانفیگ، token یا credential.
4. **تحقیق وب:** دریافت مستندات رسمی و مخازن عمومی با allowlist دامنه، محدودیت اندازه/زمان، ثبت URL و تاریخ، و جداسازی محتوای غیرقابل‌اعتماد از دستورهای سیستمی مدل.
5. **دروازه تغییر کد:** مدل فقط unified diff تولید می‌کند. Patch در worktree جداگانه اعمال می‌شود؛ مسیر traversal، فایل‌های حساس، secret، مجوزها، dependency و حجم تغییر بررسی می‌شوند.
6. **اعتبارسنجی:** Python tests، Flutter tests، analyzer، بررسی مجوز/secret و Android build. شکست هر مرحله یعنی رد patch و ارائه log به مدل برای دور بعدی؛ سقف تلاش و زمان برای جلوگیری از loop بی‌نهایت لازم است.
7. **GitHub:** فقط با مجوز حداقلی و token ذخیره‌شده در Android Keystore/secret manager، شاخه جدا و PR ایجاد شود. هیچ token نباید وارد prompt، log یا patch شود.
8. **ارتقای خود مدل/عامل:** مدل جدید ابتدا در sandbox با مجموعه آزمون ثابت، آزمون امنیتی و مقایسه کیفیت سنجیده می‌شود. نسخه قبلی نگه داشته می‌شود و rollback ممکن است. مدل حق تغییر policy، حذف تست‌ها یا تأیید خودش را ندارد.

## چرخه اجرایی هدف

`Collect evidence → Retrieve project context → Research → Model reasoning → Generate diff → Patch gate → Isolated tests/build → Review → PR → staged adoption → monitor/rollback`

مدل باید از خطاهای build و runtime یاد بگیرد، اما «یادگیری» به معنی بازآموزی خودکار وزن‌های مدل نیست؛ حافظه تجربی و به‌روزرسانی کنترل‌شده مدل دو فرایند جدا هستند.

## محدودیت نسخه فعلی مخزن

در سورس فعلی ابزارهای `diagnose_build.py`، `patch_gate.py` و `repair_orchestrator.py` وجود دارند. این‌ها به‌ترتیب گزارش خطا استخراج می‌کنند، patch پیشنهادی را از نظر ساختار/مسیر/secret بررسی می‌کنند و آن را در کپی موقت تست و build می‌کنند. اما **مدل زبانی کدنویس محلی، runtime استنتاج، اتصال مدل به ابزارها، تولید خودکار patch توسط مدل و چرخه خودکار GitHub هنوز پیاده‌سازی نشده‌اند**. بنابراین این مخزن در وضعیت فعلی نباید ادعا کند که اپ خودش کد می‌نویسد یا خودش را ارتقا می‌دهد.

## شرط پذیرش مهندس خودمختار

- inference واقعی مدل کدنویس روی دستگاه/runtime محلی، بدون API پولی اجباری؛
- تولید patch چندفایلی از روی گزارش خطا و context واقعی؛
- تست مثبت و منفی برای خطاهای شناخته‌شده؛
- هیچ تغییر خودکار در فایل‌های امنیتی/امضا/مجوز بدون تأیید انسانی؛
- build موفق و artifact قابل بازتولید؛
- PR با خلاصه تغییر، شواهد، نتایج تست و rollback plan؛
- عدم ادعای خودمختاری تا وقتی این مسیر end-to-end روی CI و دستگاه آزمایش نشده است.

## اولویت بعدی توسعه

ابتدا انتخاب و ادغام یک runtime مدل کدنویس متن‌باز با مجوز سازگار و مدل متناسب با RAM واقعی دستگاه؛ سپس adapter استنتاج، ابزارهای context/retrieval، حلقه patch/test و اتصال امن GitHub. مدل و وزن‌ها باید جدا از APK و با checksum و نسخه‌بندی توزیع شوند تا APK بی‌جهت حجیم نشود.
